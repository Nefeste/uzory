# Как ведётся работа

**Состояние:** проект. Процесс унаследован от «Вотчины» и поправлен на то, что здесь
с первого дня есть деньги (подписка), а кроме кода есть второй поток работы — **картинки**.

## Жизненный цикл возможности

Как во всех проектах студии: спецификация → код и тесты → проверка → документы → версия и выпуск
([устав, «Жизненный цикл возможности»](https://github.com/Nefeste/gornitsa/blob/main/docs/04-process.md#жизненный-цикл-возможности)).
Здесь: спецификация — по образцу [`specs/README.md`](specs/README.md); сначала движок, потом
приложение; проверки — [`06-testing.md`](06-testing.md); правятся затронутые `02`–`04`, `08`–`10`;
выпуск — по чек-листу ниже.

## Второй поток: картинки

Новые картинки — не спецификации, а записи в `content/` по правилам
[`09-content.md`](09-content.md). Порядок:

1. Карточка YAML и уменьшенный исходник — в ветке, как любой код.
2. Ассистент собирает наборы, проверяет каждую картинку и прикладывает к PR **лист превью**
   (`bun tools/content/sheet.ts`) — все новые картинки одной страницей, в обоих стилях.
3. **Владелец смотрит лист** и отвечает в PR: «да» или что поправить (кадр, число нитей,
   убрать). Картинка без «да» владельца в выпуск не идёт. С 0.9.0 то же можно в «Листе узоров»
   сборки для проверки (APK или <https://gornitsa.games/uzory/test/>): у каждой картинки —
   «Да», «Нет» или «Позже», вверху — «Скопировать решения»; текст вставляется в сообщение
   ассистенту, и тот ставит `approved` в карточки.
4. После слияния — набор недели выкладывается на сервер (ниже, «Выкладывание наборов»).

Ритм после 1.0 — **один набор в неделю**, около десяти картинок: каждый продлевает календарь
картинок дня на неделю ([`09-content.md`](09-content.md), «Календарь картинок дня»).

## Версии

`app.json` (`expo.version`, `expo.android.versionCode`) и `package.json` держат один номер;
тест сверяет их с `src/version.ts` и разделом версии в `README.md` (как в «Вотчине»).

- **0.x** — внутренние сборки: владелец и закрытый тест, APK из Releases.
- **1.0.0** — первый выход в RuStore. С него обещание постороннему человеку: работа,
  начатая в 1.x, открывается во всех 1.x, а наборы с сервера либо подходят версии,
  либо она честно говорит «обновите» ([`03-server-api.md`](03-server-api.md), «Совместимость»).
- Третье число — исправления, второе — заметная возможность, первое — смена обещания.
  0.0.x — только прототипы (0.0.1–0.0.5); с 0.1.0 заметная возможность поднимает второе
  число, даже если в дорожной карте её не было (поправка владельца, 29.09.2026: веб-версия
  и «Свой узор» шли третьим числом). Вехи 0.2–0.5 в [`07-roadmap.md`](07-roadmap.md) — цели,
  а не зарезервированные номера: пришла возможность раньше вехи — номера вех сдвигаются.
- `versionCode` — +1 на каждую сборку, ушедшую в магазин.

Каждой версии — раздел в корневом `README.md`: что изменилось для игрока, человеческим
языком. Этот же текст идёт в «Что нового» RuStore. Наборы картинок версий не получают:
у них свой номер недели (`w2026-41`).

## Ветки

`main` — всегда то, что можно выпустить. Работа идёт в ветках (`claude/<задача>` у ассистента),
в `main` — через PR. Кто сливает — по классу изменения (устав,
ADR [0018](https://github.com/Nefeste/gornitsa/blob/main/adr/0018-change-classes-automerge.md)):

- PR без путей владельца из [`.github/CODEOWNERS`](../.github/CODEOWNERS) сливается сам:
  `automerge.yml` включает auto-merge GitHub (squash), когда проверки на PR зелёные, а Ревьюер —
  другая сессия, не автор PR, — поставил метку `ревью: ок`. Новый коммит в PR снимает метку
  и auto-merge: нужно новое ревью.
- PR с путями владельца — `deploy/`, `.github/`, `server/`, `src/money/`, `store/forms.md`,
  политика конфиденциальности (`store/privacy*`, `store/site/privacy*`), `app.json`,
  `eas.json` — сливает только владелец; защита `main` требует его ревью. Код покупки
  (RuStore Pay), когда появится, — в `src/money/`.

**На каждый PR — проверки** (`pr.yml`; устав,
ADR [0019](https://github.com/Nefeste/gornitsa/blob/main/adr/0019-ci-on-pr.md)): типы, линтер
и тесты — команды из `AGENTS.md`, без сборки APK. Проверка обязательна для слияния и отвечает
на каждом PR; PR только с `docs/` и `research/` пропускает её шаги внутри задачи — эти файлы
не читает ни один тест. Перед каждым push ассистент всё равно гоняет у себя типы, линтер, тесты
и веб-сценарий: CI на PR — сетка, а не замена.

Слияние, которое включило автослияние, GitHub делает от имени токена Actions (`GITHUB_TOKEN`),
а события этого токена workflow на push не запускают. Поэтому после слияния ничего не ждёт
push в `main`: APK собирается на тег версии, веб-версия для сайта — по расписанию.
Вручную (Actions → Run workflow) запускаются `site.yml`, `content.yml`, `content-fetch.yml`
и `rustore.yml`; у сборки APK (`android.yml`) ручного запуска нет — только тег (устав,
ADR [0019](https://github.com/Nefeste/gornitsa/blob/main/adr/0019-ci-on-pr.md); решение
владельца 03.10.2026).

## Автоматика

| Workflow | Когда | Что делает |
|---|---|---|
| `pr.yml` | на каждый PR в `main` | типы, линтер, тесты движка и картинок со сборкой встроенного набора — обязательная проверка перед слиянием; PR только с `docs/` и `research/` проходит её без шагов |
| `automerge.yml` | метка `ревью: ок`, новый коммит в PR, конец проверок на PR | при метке, зелёных проверках и без путей владельца — auto-merge GitHub (squash); новый коммит снимает метку и auto-merge |
| `android.yml` | только на тег `vX.Y.Z` | типы, линтер, тесты движка и картинок; сборка встроенного набора; веб-сборки от корня и для папки `/uzory/test` со сценарием Playwright; prebuild, Gradle, APK со встроенным набором только из отобранного (`--release`); проверки файла: подпись постоянным ключом, разрешения по белому списку, выравнивание библиотек под 16 КБ, `allowBackup="true"` с правилами копии, размер APK; релиз «Узоры X.Y.Z» в Releases (тег должен совпасть с версией в `app.json`). AAB не собирается, пока нет Google Play (решение владельца 03.10.2026); вернуть — строкой матрицы в задании «Ключ подписи» |
| `site.yml` | раз в сутки, если `main` ушёл вперёд от выложенного; вручную | закрытая веб-версия — сборка `main` для сайта; прошла сценарий Playwright — зашифрованная ключом сервера, в ветку `vps` ([спецификация](specs/2026-09-web.md)) |
| `content.yml` | раз в сутки, если `main` ушёл вперёд от прошлого успешного запуска; вручную — только на `main` (с галочкой «base» — первый каталог) | с 0.13.0: золотой тест выпущенных узоров по каталогу с сервера; если в `content/week.yaml` ещё не выпущенный набор — сборка набора недели и каталога, подпись, выкладка на сервер и сверка скачиванием; скрипт свёртки счётчиков — на сервер. Пока каталога на сервере нет и набора недели нет — заканчивается за секунды, ничего не собирая (ниже, «Выкладывание наборов») |
| `rustore.yml` | вручную | кладёт APK из Releases в черновик новой версии RuStore (`tools/store/rustore.mjs` из «Вотчины») |
| `content-fetch.yml` | вручную: ассистент запускает на своей ветке, когда добавил карточки | скачивает исходники, названные в карточках (до 2000 точек; с галочкой «again» — и уже скачанные, заново); с «search» — ищет кандидатов с лицензиями (`content/candidates.json`); с «dims» — размеры холстов картин из Викиданных (`content/dimensions.json`); коммитит в ту же ветку — среда ассистента Викисклад, Викиданные и Библиотеку Конгресса не видит. Ничего не собирает |

Сценарий в браузере идёт в `android.yml` на теге и в `site.yml` перед выкладкой веб-версии;
`content.yml` — с 0.13.0.

**Ветка `vps`** — только для сервера сайта: один коммит без истории, `test.tar.gz.age`
(веб-сборка, зашифрованная открытым ключом сервера <https://gornitsa.games/.well-known/uzory-age.pub>)
и `build.json` с коммитом `main`. Пишет её только `site.yml`, каждый раз затирая прежнюю; руками
её не трогают. Сборку в открытом виде CI никуда не выкладывает — ни в ветку, ни в артефакты:
в ней картинки «только для проверки», а артефакты открытого репозитория скачивает кто угодно.
По той же причине APK собирается с `--release` — только с картинками и пьесами с «да»
и правами ([`09-content.md`](09-content.md), §8), — а снимки сценария Playwright уходят
в артефакты, только когда репозиторий закрыт.
Ключа на сайте нет (сайт ещё не настроен) — предупреждение в итогах запуска, сборка
не выкладывается. `rustore.yml` уже есть, но первую версию RuStore принимает только
через консоль ([`store/preorder.md`](../store/preorder.md)). Без ключа в секретах APK на теге
собирается только на проверку (подпись отладочная, файл выбрасывается), с ключом —
подписанный и в Releases.

**Минуты Actions.** Сейчас репозиторий открытый: минуты обычных раннеров GitHub не считает. Но
всё в нём видно всем — и код, и журналы запусков; поэтому снимки на отбор идут черновиком
релиза ([`09-content.md`](09-content.md), «Свои снимки»), а ключи — только секретами. По уставу
игры закрыты (ADR [0017](https://github.com/Nefeste/gornitsa/blob/main/adr/0017-repo-visibility.md)),
а закрытые репозитории владельца делят 2000 минут в месяц. Проверки на PR — 7 минут (замер
03.10.2026: сборка картинок — 1:41, тесты — 4:06, из них две полные сборки теста
одинаковости); PR только с документами — минута. Автослияние — минута на каждый конец
проверок PR и на метку. Весь `android.yml` на тег — около 20 минут (Gradle — 10–15, два
веб-сценария, проверки), веб-версия для сайта со сценарием — около 7 минут в те сутки, когда
`main` менялся.

**Белый список разрешений APK**: `INTERNET` (каталог и наборы), `ACCESS_NETWORK_STATE`,
`VIBRATE`, `MODIFY_AUDIO_SETTINGS` (`expo-audio`, как у «Анамнеза») и служебные разрешения,
которые приносят RuStore Pay и Review SDK (список фиксируется после первой сборки).
**Запрещены** и вырезаются в `app.json`: `AD_ID` (рекламы нет — ADR [0008](adr/0008-no-ads.md)),
`WAKE_LOCK` (его приносит плеер `expo-audio`, а игре он не нужен), доступ к файлам,
камере, контактам, показ поверх окон. Новое разрешение сборка не пропустит: нужное
добавляется в список в `android.yml`, сюда и в политику конфиденциальности.

## Секреты и переменные репозитория

| Имя | Что | Где взять |
|---|---|---|
| `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` | постоянный ключ подписи (ADR [0014](adr/0014-permanent-app-id-and-key.md)) — названия как у «Вотчины» | создать один раз; копию хранить у владельца отдельно |
| `ANDROID_CERT_SHA256` (переменная) | отпечаток сертификата: чужой ключ остановит сборку | из ключа |
| `DEPLOY_SSH_KEY`, `DEPLOY_HOST` | выкладывание наборов и скрипта свёртки на сервер студии (`content.yml`) | ключ пользователя `deploy`, его создаёт `deploy/setup-server.sh` сайта |
| `DEPLOY_KNOWN_HOSTS` (переменная) | ключ сервера для SSH — без неё ключ принимается без сверки (выложенное всё равно сверяется скачиванием) | `ssh-keyscan -t ed25519 <сервер>` — одна строка |
| `CATALOG_SIGNING_KEY` | закрытый ключ Ed25519 для подписи каталога ([`03-server-api.md`](03-server-api.md)) | создать один раз у себя: `bun tools/content/keygen.ts`; копию хранить у владельца отдельно; открытый ключ — в `src/state/keys.ts` (В18) |
| `RUSTORE_API_TOKEN`, `RUSTORE_KEY_ID` | загрузка в RuStore | консоль RuStore → «API RuStore» |
| `RUSTORE_APP_ID` (переменная) | приложение в RuStore Pay | консоль RuStore |

### Как завести ключ подписи (один раз, В8)

```bash
keytool -genkeypair -v -keystore uzory-release.jks -alias uzory \
  -keyalg RSA -keysize 4096 -validity 36500 \
  -dname "CN=Gornitsa, O=Gornitsa, C=RU"            # спросит два пароля — записать
base64 -w0 uzory-release.jks > uzory-release.jks.b64    # macOS: base64 -i uzory-release.jks
keytool -list -v -keystore uzory-release.jks -alias uzory | grep SHA256
```

`keytool` — из JDK 17 или из Android Studio (`jbr/bin`). В Windows вместо `base64` —
PowerShell, строка сразу попадёт в буфер обмена:
`[Convert]::ToBase64String([IO.File]::ReadAllBytes("$PWD\uzory-release.jks")) | Set-Clipboard`.

В репозитории → Settings → Secrets and variables → Actions: секреты
`ANDROID_KEYSTORE_BASE64` (содержимое `.b64`), `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_ALIAS` (`uzory`), `ANDROID_KEY_PASSWORD`; переменная `ANDROID_CERT_SHA256` —
отпечаток из последней строки. Сам файл `.jks` и пароли — в двух местах вне GitHub
(ADR [0014](adr/0014-permanent-app-id-and-key.md)): потерянный ключ — это новое приложение
в RuStore. После этого каждый тег `vX.Y.Z` собирает подписанный APK и публикует его
в Releases релизом на этот тег. Отдельной проверки ключа без тега нет: его проверяет первый
же тег версии — задание «Ключ подписи» останавливает запуск, если секреты заданы не все или
нет `ANDROID_CERT_SHA256`, а шаг «Подпись» — если отпечаток готового файла не совпал;
релиза тогда нет. Версии 0.x выходят пре-релизами, так что для проверки годится очередной
тег 0.x. Пока ни у одной картинки нет «да», сборка картинок остановится: собирать нечего.

## Выкладывание наборов

С 0.13.0 — `tools/content/week.ts` в `content.yml`. Что уже выпущено, знает сервер: каталог
и наборы скачиваются с `https://gornitsa.games/uzory/v1/`, подпись каталога проверяется ключами
из `src/state/keys.ts`. В репозитории — только карточки и план недели.

**Набор недели** — PR недели: новые карточки с `approved` и `content/week.yaml`:

```yaml
id: w2026-42          # неделя даты from по ISO; второй набор той же недели — w2026-42-2
from: "2026-10-12"    # с этой даты картинки набора видны в библиотеке (не раньше слияния)
days: 7               # на сколько дней продлить календарь картинок дня (по умолчанию 7)
pin:                  # праздник с плавающей датой, день рождения художника — по желанию
  "2026-10-14": kids-matryoshka
notice: null          # строка на главной — только если нужна (03-server-api.md)
```

В том же PR — узоры набора в списке выпущенного у золотого теста
(`tools/test/fixtures/released.json`, ADR [0010](adr/0010-frozen-patterns.md)): их вписывает
`bun tools/content/week.ts --released https://gornitsa.games/uzory/v1/ --freeze` — он же
показывает, какие картинки и дни календаря войдут в набор. Так изменившийся выпущенный узор
ловят тесты ещё до слияния.

Набор выкладывается в ночь после того, как в `main` пришёл `week.yaml` с ещё не выпущенным `id`,
или сразу — Actions → Content → Run workflow; меток не нужно, тот же `id` второй раз
не выкладывается. `content/week.yaml` — путь владельца в `CODEOWNERS`: набор уходит игрокам,
поэтому PR недели сливает владелец (устав, ADR 0018). `content.yml`:

1. собирает картинки с «да» и сверяет **золотым тестом**: картинка, чей ключ `id@v` уже
   выпущен, собирается в те же клетки и нити — иначе у игроков под одним ключом разошлись бы
   узоры, и запуск останавливается («поднимите v в карточке»);
2. собирает набор недели — картинки с «да», чьих ключей нет ни в одном выпущенном наборе
   (новые и новые версии), с датой `from` — и продлевает календарь картинок дня: со дня после
   конца выпущенного (не раньше `from`) на `days` дней, картинками всех наборов, ещё не бывшими
   картинкой дня, по правилам сборки ([`09-content.md`](09-content.md), §9), без той же
   коллекции на стыке и с днями из `pin`;
3. собирает новый `catalog.json` — выпущенные наборы как были и новый в конце — и подписывает
   его ключом `CATALOG_SIGNING_KEY` (`catalog.sig`); открытой половины ключа нет в
   `src/state/keys.ts` — останавливается: телефоны такой каталог не примут;
4. копирует **сначала наборы (выложенные не переписываются), потом подпись и каталог** в
   `/srv/gornitsa/uzory/v1/` по `rsync` через SSH — телефон никогда не увидит каталог со ссылкой
   на ещё не выложенный набор. Папка — вне папки сайта: автообновление сайта выкладывает свою
   папку с `--delete` и стёрло бы наборы;
5. скачивает каталог, подпись и все наборы из него обратно с сайта и сверяет SHA-256 —
   выложено то, что собрано.

Без набора недели запуск только сверяет выпущенное (п. 1) — в ту ночь, когда `main` менялся.
Пока на сервере нет каталога, сверять не с чем.

**Первый каталог** — к выпуску 1.0, один раз: в PR выпуска `--base --freeze` вписывает узоры
встроенного набора в список выпущенного, после слияния — Actions → Content → Run workflow на
`main`, галочка «base». В каталоге — встроенный набор этой версии с `builtin: true` (телефоны его не
качают), календарь — до конца его календаря, `minApp` — эта версия. Встроенный набор следующей
версии (этап 1.1) собирается уже по выпущенному: только выпущенные картинки и выпущенный
календарь, — иначе прежние версии не получили бы его картинок.

Руками то же самое: `CATALOG_SIGNING_KEY=… bun tools/content/week.ts --released
https://gornitsa.games/uzory/v1/` (с `--check` — только сверка, с `--base` — первый каталог)
собирает в `dist/v1/`; `bun tools/content/week.ts --verify https://gornitsa.games/uzory/v1/`
сверяет выложенное с `dist/v1/`.

Откат — прежний `catalog.json` с его `catalog.sig` (они в артефактах запуска:
`previous-catalog.*`): наборы не удаляются никогда, достаточно вернуть каталог и подпись.

На сервере для `/uzory/` в конфигурации nginx сайта — отдельный журнал без адресов
для каталога, заголовки кэша ([`03-server-api.md`](03-server-api.md)) и gzip для наборов.
Эти строки живут в репозитории сайта (`deploy/nginx/gornitsa.games.conf`) и правятся там.
Там же — пользователь `deploy`, владелец `/srv/gornitsa/uzory/` (`v1/` и `stats/`), с ключом
для CI (В9); таймер свёртки — [`server/stats/README.md`](../server/stats/README.md), сам
`fold.ts` кладёт туда `content.yml`.

## Счётчики

Раз в сутки скрипт на сервере сворачивает журнал каталога в CSV
([`04-data-model.md`](04-data-model.md), «Счётчики на сервере»). Владелец смотрит сводку
раз в неделю, первые четыре недели после выхода — каждый день:

- **установки недели** — сумма запросов с `d = 0` для недели `c`;
- **D1 и D7** — сумма с `d = 1` (с `d = 7`), делённая на установки той же недели;
- **D30** — средняя доля за 30–59-й дни: сумма с `d = 30-59`, делённая на 30 × установки;
- **активные за день** — все запросы дня; **доля подписчиков** — запросы с `p = 1`;
- **картинок и минут на активного** — по корзинам `f` и `m`.

Скрипт — `server/stats/fold.ts` этого репозитория (с 0.8.0), таймер и строки nginx —
[`server/stats/README.md`](../server/stats/README.md); выкладывается вместе с наборами,
таблица `stats.csv` живёт на сервере рядом с наборами.

## Выпуск версии — чек-лист

1. Спецификация отмечена «сделано», документы поправлены, раздел версии в `README.md` написан.
2. Все проверки [`06-testing.md`](06-testing.md) зелёные.
3. Встроенный набор собран из `main`, календарь картинок дня расписан минимум на 120 дней
   вперёд ([`09-content.md`](09-content.md)).
4. Сборка поставлена на опорный телефон с RuStore: покупка в тестовом режиме RuStore Pay,
   восстановление покупки после переустановки, окончание подписки (начатое дошивается),
   работа без сети, скачивание набора, крупный шрифт, большая картинка — от начала до конца.
5. Тег `vX.Y.Z` → CI собирает и публикует в Releases → `rustore.yml` кладёт черновик →
   владелец проверяет «Что нового» и отправляет на модерацию.
6. После выхода — неделя наблюдения: отзывы, письма «Сообщить об ошибке», счётчики.

## Отзывы в RuStore

На отзывы 1–3★ владелец отвечает в течение двух дней: что случилось и что сделано.
Повторяющаяся жалоба — задача в дорожную карту. Просьба «добавьте картинки про …» —
в список тем для набора недели ([`09-content.md`](09-content.md), «Отбор»).
